# 外部项目评估（评估 / repo）提示词策略

> 适用：在别处看到感兴趣的 GitHub / GitLab / Gitee / 项目主页，想知道「它是什么、和我现在的环境搭不搭、值不值得接进来」。
> 定位：这是本插件内置的第 5 个场景（chips 里显示为「评估」），既用于 DSH 输入框的「优化提示词」按钮，也同步在 `skills/prompt-optimizer/SKILL.md` 的 agent 版里。

## 1. 为什么单开一个场景

这类提问的真实意图链是固定的五步：

> 它是什么 → 它现在是什么状态（版本、维护、许可）→ 和我现在的环境搭不搭 → 怎么最小代价验证 → 到底用不用

但草稿通常只有一句话加一个链接（「这个能用吗」「值得上吗」）。不加工直接发给 agent，常见四种失败：

| 失败模式 | 具体表现 | 后果 |
|---|---|---|
| 百科式介绍 | 把 README 复述一遍，没有结论 | 看完还是不知道用不用 |
| 凭记忆报数 | 张口就说「最新版 2.x、支持 Windows、和你的插件不冲突」 | 版本号 / 兼容性可能是幻觉 |
| 无视环境 | 给 Linux 的 `apt install`，或忽略沙箱不能写系统目录 | 建议不可执行 |
| 只有结论没有验证 | 说「能用」但不说怎么验证、失败怎么办、替代方案是什么 | 决策不可复核 |

论文场景优化的是「论证链 + 证据等级」，派活场景优化的是「交付物 + 验收」，都不覆盖「带环境约束的引入决策」。所以单独开一个场景，把一句话改写成一条**可执行的决策链**。

## 2. 已有人做过什么，差异在哪

2026-11 检索到的同类实现（都在做「分析产物」，不是「改写提问」）：

- **360 SkillHub「Repo Analysis」**（作者 9penny，<https://skillhub.360.com/skills/repo-analysis>）：面向仓库的工程化分析技能，三模式「速读版 / 架构版 / 接手评审版」，强调「已确认 / 推测 / 待验证」证据阶梯，GitHub 健康度只作可选轻量补充。它是让 agent 替你把仓库读一遍。
- **`Amey-Thakur/AI-SKILLS` 的技术尽调提示词**（<https://github.com/Amey-Thakur/AI-SKILLS/blob/main/prompts/technical-due-diligence.md>）：存在一个 technical-due-diligence prompt 加配套 command；抓取时网络失败，细节未核实。
- **`davidortinau/awesome-copilot`**（<https://github.com/davidortinau/awesome-copilot>）：收录 GitHub / 仓库管理类 prompts，DeepWiki 有 Task-Specific Prompts 索引；中文社区另有「开源项目选型矩阵」类文章。

差异：以上都是「让 agent 去做一次完整仓库分析」；本插件做的是**把用户的一句模糊提问改写成可粘贴执行的评估提示词**，产出物是提示词本身，并且强制三件事——环境硬约束逐项对照、最小验证命令与回滚、三选一结论 + 可证伪条件。仓库分析技能可以作为被派活的执行方，两者不冲突。

## 3. 判定规则（什么时候算「评估」）

| 草稿特征 | 判成 | 理由 |
|---|---|---|
| 项目链接 / 明确项目名 + 「用不用 / 适合我吗 / 能不能接进来 / 要不要换」 | **评估** | 核心决策是引入，不是写代码 |
| 出现专业术语、剂量 / 数据 / 机制 / 审稿措辞 | 论文 | 改稿、证据等级、机制推断 |
| 明确动作 + 交付物（输出格式、文件名、清单、命令、判定标准） | 派活 | 有可验收产物 |
| 一句话、无交付物、不支撑决策 | 日常 | 只需短答 |
| 拿某个仓库当代码来源，让我改代码 / 改文档 | 派活 | 仓库是素材，不是评估对象 |
| 整段英文 | 英文（叠加） | 语言维度，实质场景照常判 |

边界案例：

- `链接 + 帮我改成能跑的样子` → 派活（交付物是改好的代码，不是「用不用」的结论）。
- `论文里引用了这个仓库，核对版本与引用` → 论文（核对引用，不是引入决策）。
- `这个仓库的方法能不能写进我的论文` → 评估（有引入意图），结论里必须分开「工具能跑通」与「结果可用于论文」。

## 4. 五段策略

### 段 1：身份（先锁定评估对象）

- 要：owner/name、官方主页；排除同名仓库、镜像、fork、已归档旧仓库。
- 禁止：拿二手转载的链接当官方来源；不确定时猜一个「大概是这个」。
- 给不出就写【待补：准确链接】。身份错了，后面每一段都白写——这是把身份放在第一位的原因。

### 段 2：一手证据 + 时效

- 要：事实只取一手材料——README、releases / tags、LICENSE、依赖清单、最近 commit、开放 issue；每条写核查日期。
- 禁止：凭记忆报版本号、star 数、API、平台兼容性；把第三方博客、营销文章当一手证据。
- 拿不到就标「未核实」；没联网 / 没权限读仓库，写成能力缺口，不许猜。

### 段 3：环境硬约束（先事实，后对照）

- 要：先列出环境事实——OS 与版本、运行时 / 包管理器版本、已有依赖与插件体系、权限 / 沙箱 / 网络边界；草稿没给的标【待补】。
- 再逐项对照项目要求，每项给三态之一：「匹配 / 需额外配置 / 冲突」，并写依据。
- 为什么先列事实：不列事实就会写出「在 Linux 上 apt install」这种不可执行的建议；事实和对照分开，错在哪一步一眼可见。

### 段 4：最小验证

- 要：临时目录（或可回滚位置）、原样可跑的命令、通过判据、失败怎么回滚。
- 禁止：「建议你先试试」这种没有命令、没有判据的验证。
- 原则：用最小一步换最大确定性，验证成本要低于引入成本。

### 段 5：结论与反证

- 要：三选一——「现在能用 / 改造后用（成本 + 第一刀改哪）/ 不用（替代方案）」；写前提与可证伪条件（什么证据会推翻这个结论）。
- 科研用途再加一层：把「工具能跑通」与「结果可用于论文（稳定性、可重复性、证据边界）」分开写。
- 禁止：用 star 数、热度、README 营销话术当结论；只推荐不写前提；写社区运营 / 融资 / 生态排名这类与本次决策无关的维度。

## 5. 三组改写示例

每组 after 都 ≤700 字，含 3 行验收表，可直接粘贴使用。示例里的占位链接只是演示形态，实际使用时换成你要评估的仓库。

### 例 A：DSH 插件（看别人推荐的插件能不能装）

**before**

> 在推特看到有人推荐 https://github.com/acme/dsh-focus-mode 插件，我的环境能用吗？和现在装的插件会不会冲突？

**after**

```text
评估 https://github.com/acme/dsh-focus-mode（示例占位链接；先确认 owner/name 与官方主页，排除同名与 fork）能否装进我当前的 DSH 桌面环境。

环境事实（草稿没给的先列出来，缺的标【待补】）：Windows 11 + DSH 桌面 0.2.2 级别（Web GUI http://127.0.0.1:18401）；已装插件含 prompt-optimizer-button（link 方式，desktop profile）；Node / pnpm 可用；沙箱为 workspace-write。

1. 事实（写核查日期，拿不到标「未核实」，不许凭记忆）：README 定位与安装方式、releases 最新版本、LICENSE、engines.dsh 与 dsh.client 声明、最近 commit、开放 issue 里与 Windows / 兼容性相关的条目。
2. 环境对照（每项给「匹配 / 需额外配置 / 冲突」+ 依据）：DSH 版本区间是否覆盖 0.2.2；是否注册同一个 slot 或改写 composer DOM（与本插件冲突风险）；安装依赖是否需要管理员权限或网络代理；是否触发沙箱写盘限制。
3. 最小验证：在临时 profile 或按 disable → enable 的顺序装一次，给原样命令与成功判据（plugin_manager 返回 application:"applied"、页面出现 UI、控制台无报错）；失败时如何 remove / 恢复 link。
4. 结论三选一：现在能用 / 改造后用（成本、第一刀改哪）/ 不用（替代方案），写清前提与可证伪条件；不许用 star 数或 README 宣传语当结论。

## 验收标准
| 检查项 | 合格标准 | 不合格的样子 |
|---|---|---|
| 事实可核对 | 每条事实带版本号与核查日期 | 只写"这个插件很火" |
| 冲突有依据 | 指明 slot / DOM / 依赖冲突点 | 泛泛说"可能冲突" |
| 可回滚 | 给出卸载与恢复步骤 | 直接让你装 |
```

### 例 B：科研 Python 工具（值不值得接进影像分析流程）

**before**

> https://github.com/AIM-Harvard/pyradiomics 这个能用来做我 SBRT-RDN 的影像组学吗，值得上吗

**after**

```text
评估 https://github.com/AIM-Harvard/pyradiomics 是否值得引入 SBRT-RDN 的影像分析流程（先确认 owner/name 与官方主页，排除 fork 与已归档旧仓库）。

环境事实：Windows 11；Python 版本【待补】；已有依赖【待补】；GPU【待补】；沙箱 workspace-write（安装与临时文件只能落工作区）；数据为 DSA / 影像资料，样本量【待补】。

1. 事实（核查日期，拿不到标「未核实」）：最近 release 与维护状态、支持的 Python 版本、Windows wheel 情况、核心依赖（SimpleITK / numpy 等）与体积、LICENSE、开放 issue 里的已知坑。
2. 环境对照（匹配 / 需额外配置 / 冲突 + 依据）：Python 版本与 wheel 是否覆盖 Windows；依赖体积与编译需求；与现有分析环境是否冲突；离线安装可行性。
3. 最小验证：在临时目录用 1 例影像跑通特征提取，给原样命令、输出特征数量与耗时的通过判据、失败回滚（删除虚拟环境）。
4. 研究适用性：把「工具能跑通」与「结果可用于论文」分开——特征稳定性 / 可重复性（ICC、扫描参数敏感性）、样本量与过拟合风险、能否写进方法学并给出证据边界；给替代方案（如已有工具链）。
5. 结论三选一（现在能用 / 改造后用 + 成本与第一刀 / 不用 + 替代），写前提与可证伪条件，不许用 star 数或"医学影像标配"这类话术当结论。

## 验收标准
| 检查项 | 合格标准 | 不合格的样子 |
|---|---|---|
| 事实可核对 | 版本 / 日期 / 维护状态有来源 | 只写"很流行" |
| 环境匹配有依据 | 逐项说清 Windows / Python 版本 | 直接给 Linux 命令 |
| 科研边界清楚 | 分开"跑通"与"可发表" | 跑通即认定可用 |
```

**before**

## 验收标准
| 检查项 | 合格标准 | 不合格的样子 |
|---|---|---|
| 事实可核对 | 版本号 + 获取方式 + 日期 | 只给主页链接 |
| 环境匹配有依据 | 说清权限与 PATH 处理 | 一句"支持 Windows" |

## 6. 在插件里怎么用

1. 把上面那种一句话草稿贴进输入框，点星星 → 自动判成「评估」时会直接按这条链改写；
2. 判偏了：点开面板，点 chips 里的「评估」钉住，再点一次星星重跑（钉住只影响下一次）；
3. 想让所有评估都带上你的固定环境：点「评估」chip 的 `✎`，在「说明 / 提示词」里追加，例如「我的环境固定为 Windows 11 + DSH desktop + workspace-write；评估必须给最小验证命令与回滚步骤」。内置规则仍然生效，说明叠加在后面；
4. 重命名：`✎` 里把「评估」改成「选型 / 尽调」都行，只改显示名不改行为；
5. 换环境 / 换团队模板：点 chips 末尾 `＋` 新建自定义场景，把整段评估模板放进「说明」；
6. Codex 等没有输入框插件的客户端：用 `skills/prompt-optimizer/SKILL.md`，规则与宿主侧一致。

## 7. 怎么验证策略生效

拿 3 个测试草稿各跑一次，after 必须同时满足：

- [ ] 有身份确认（owner/name、官方主页或【待补】），没有把镜像 / fork 当官方；
- [ ] 事实带核查日期；没核实的标「未核实」；没有凭记忆报版本 / star；
- [ ] 环境事实先列出，对照逐项给「匹配 / 需额外配置 / 冲突」+ 依据；
- [ ] 有最小验证的原样命令、通过判据、失败回滚；
- [ ] 结论是三选一 + 前提 + 可证伪条件，不是「推荐使用」；
- [ ] 文末「## 验收标准」表恰好 3 行、外部可核对；
- [ ] 正文 ≤700 字、不超过原文 1.5 倍（只有链接时按 700 字上限走）。

负面测试：给一个不存在的仓库名（如 `https://github.com/nobody/does-not-exist`），输出应写「未核实 / 无法确认」，而不是编造 star 数或版本。

本地已通过 `node _test_po_plugin.mjs`（含 pinned 与 auto 两种 repo 判定）和 `node _test_po_client.mjs`（chips 与持久化）；端到端可在重载插件后向 `POST /prompt-optimizer/rewrite` 发真实草稿检查。

## 8. 维护约定

改这套策略要同步四处，少一处就会漂移：

1. `index.js` 的 `SCENARIO_HINTS.repo`（钉住场景时注入的 user hint）；
2. `index.js` 的 `SYSTEM_PROMPT`（场景判据、场景增量、长度上限、输出枚举）；
3. `skills/prompt-optimizer/SKILL.md`（agent 版规则）；
4. 本文档与 README 的「项目评估」小节。

改完必跑：

```powershell
node --check index.js
node --check client.js
node _test_po_plugin.mjs
node _test_po_client.mjs
```
